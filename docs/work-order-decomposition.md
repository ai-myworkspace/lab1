# Work Order Decomposition

## Issue WO-201

This document defines the validation rules, persistence schema, and REST API contract for creating a work order.

## UI Validation Matrix

| Field Name | Type | Required | Rules / Constraints |
| :--- | :--- | :--- | :--- |
| `title` | String | Yes | Minimum 5 characters; maximum 255 characters |
| `description` | String | No | Maximum 2000 characters |
| `priority` | Enum | Yes | Defaults to `MED`; allowed values: `LOW`, `MED`, `HIGH`, `CRITICAL` |
| `customer_id` | UUID | Yes | Must reference a valid active customer |

The UI must prevent submission when a required field is missing or when a value violates its constraint. The selected customer must be active at validation time.

## Data Schema

PostgreSQL 16 is the target database. The application must enable the UUID generation function used by the default value before creating this table.

```sql
CREATE TABLE work_orders (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title VARCHAR(255) NOT NULL,
    description TEXT,
    priority VARCHAR(20) NOT NULL DEFAULT 'MED',
    status VARCHAR(20) NOT NULL DEFAULT 'DRAFT',
    customer_id UUID NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT chk_priority CHECK (priority IN ('LOW', 'MED', 'HIGH', 'CRITICAL'))
);
```

### Persistence Rules

- `id` is generated by PostgreSQL when a work order is created.
- `priority` defaults to `MED` when the client omits it.
- `status` defaults to `DRAFT` for every new work order.
- `created_at` records the database time at creation.
- `customer_id` is required and must be validated against the active-customer record by the service before insertion.

## REST API Contract

### Create Work Order

**Method:** `POST`  
**Path:** `/api/v1/work-orders`  
**Authentication:** `Authorization: Bearer <token>`  
**Content-Type:** `application/json`

#### Request Body

```json
{
  "title": "HVAC Repair Unit 4",
  "description": "System reporting error code E-42",
  "priority": "HIGH",
  "customer_id": "a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11"
}
```

`description` and `priority` may be omitted. If `priority` is omitted, the service persists `MED`.

#### Successful Response

**HTTP status:** `201 Created`  
**Content-Type:** `application/json`

```json
{
  "id": "c9bf9e57-1685-4c89-bafb-ff5af830be8a",
  "status": "DRAFT",
  "created_at": "2026-08-30T10:00:00Z"
}
```

The response contains the generated identifier, the initial status, and the creation timestamp. The service should include a `Location` header pointing to the created work-order resource when that resource endpoint is available.

#### Validation and Authorization Outcomes

| Condition | HTTP Status | Expected Behavior |
| :--- | :---: | :--- |
| Missing or invalid bearer token | `401 Unauthorized` | Reject the request without creating a work order |
| Missing or invalid field value | `400 Bad Request` | Return field-level validation errors |
| Customer does not exist or is inactive | `400 Bad Request` | Reject the request without creating a work order |
| Valid request | `201 Created` | Persist the work order with status `DRAFT` |

The API must not return a successful response until the customer reference has been validated and the work order has been persisted.
